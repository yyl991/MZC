## replies 收集排查 + 时间方案（02:48）
- 作者反馈新回复「时间有问题」+「好像收不到」。代码侧（7e410e3 之后）收集逻辑完好：仍上报 time/text/ip/region/uid，`getPlayerIp` 未定义走 catch→`upload("unknown")` 立即上报，无延迟。
- 时间乱序根因：`time` 是玩家设备本机时间 `new Date().toLocaleString(...)`，各设备时钟不准 + fetch 并发到达顺序≠发送顺序（id 是入库顺序）→ 同一 uid 也可能 id 大但 time 小。服务端 `created_at`（UTC）已被 drop（`select=created_at` 返回 400 列不存在），无服务器时间兜底。
- 给作者的时间方案 SQL（未在库上执行，指导作者新建 query 跑）：`alter table replies add column if not exists created_at timestamptz default now();` + 重建视图 `replies_numbered`（`nth=row_number() over(partition by uid order by id)`, `reply_time=case when created_at is not null then to_char(created_at at time zone 'Asia/Shanghai','YYYY/MM/DD HH24:MI:SS') else "time" end`, reply_text=text）；视图不暴露 created_at/ip/region。历史行 created_at 为 NULL 回退用 time。
- **RLS 诊断误报教训**：用 curl 模拟 POST 时 uid 用 `DIAG_DELETE_ME`（含下划线）→ HTTP 401 `42501 new row violates RLS policy`；改用真实格式 `DmwDiagTest12345`（纯字母数字，仿设备 ID）→ **HTTP 201 成功**。说明 replies 的 insert policy 对 uid 格式有校验（下划线被拒），真实玩家 uid 都是 Dmw+字母数字，收集正常。**以后诊断写入必须用真实 uid 格式**，否则误判服务端收不到。受控写入仅 1 条成功（`DmwDiagTest12345` / 文本「【诊断测试-请删除】」），已告知作者可在 SQL Editor `delete from replies where uid='DmwDiagTest12345'` 清理（匿名 key 无 delete 权限，我删不了）。
- 结论：改动后的收集功能没问题，服务端能正常收到；之前「收不到」是没刷新 + 我诊断 uid 格式错误的双重误报。工作区干净，未 commit/push。
